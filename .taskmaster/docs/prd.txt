# Product Requirements Document: JW Extractor - Error Handling & Retry Fix

## Problem Statement
Extraction sometimes fails and requires 2-3 manual attempts to succeed. Error messages are generic and don't help identify what went wrong (network, parsing, conversion, etc.).

## Goal
Fix extraction reliability with automatic retries and provide better error messages so we can actually debug issues.

## Scope (Minimal Fix)
This is a focused bug fix, NOT a major rewrite. Keep changes minimal and surgical.

## Core Requirements

### 1. Enhanced Error Types & Messages
**Current Problem:**
- Only 3 error types (INVALID_URL, CONTENT_NOT_FOUND, NETWORK_ERROR)
- Generic messages like "An unexpected error occurred"
- Can't tell if it was network, timeout, parsing, or conversion that failed

**Solution:**
- Add specific error types:
  - FETCH_ERROR (network connection issues)
  - TIMEOUT_ERROR (request timeout)
  - PARSE_ERROR (HTML parsing failed)
  - CONVERSION_ERROR (Markdown conversion failed)
- Include basic context:
  - Which stage failed (fetch, parse, convert)
  - Attempt number if retrying
  - Timing information

**Implementation:**
- Extend the ErrorType enum in `src/lib/types.ts`
- Add optional `stage` and `attemptNumber` fields to error object
- Update error messages to be more specific

### 2. Automatic Retry Logic
**Current Problem:**
- Single attempt, then fails
- User must manually retry 2-3 times
- No exponential backoff or smart retry strategy

**Solution:**
- Wrap extraction in retry handler
- Maximum 3 attempts
- Exponential backoff: 1s, 2s, 4s between attempts
- Only retry on transient errors (timeout, network, parse)
- Don't retry on permanent errors (invalid URL)

**Implementation:**
- Create simple `src/lib/extraction/retry-handler.ts` utility
- Add retry wrapper around existing extraction logic
- Show "Retrying (attempt 2 of 3)..." to user

### 3. Basic Logging for Debugging
**Current Problem:**
- No visibility into what's happening during extraction
- Hard to debug production issues

**Solution:**
- Simple console logging in development
- Log key stages: fetch start/end, parse start/end, convert start/end
- Log timing for performance visibility
- Log which retry attempt succeeded

**Implementation:**
- Create minimal `src/lib/extraction/logger.ts` with console.log wrappers
- Add timing logs at each stage
- Include in error context

### 4. Simple HTML Parsing Fallback (Optional)
**Current Problem:**
- If `#content.content` selector fails, extraction fails
- HTML structure might have variations

**Solution (Keep It Simple):**
- Try `#content.content` (current)
- If that fails, try `#content` (without .content class)
- If that fails, try `article` tag
- Log which selector worked

**Implementation:**
- Add fallback selector array to existing parse logic
- Try each selector in order until one returns content
- Log which worked for debugging

### 5. Markdown Conversion Error Handling
**Current Problem:**
- If Turndown conversion fails, entire extraction fails
- No error recovery

**Solution:**
- Wrap Turndown in try-catch
- On error, attempt conversion with simpler rules
- Final fallback: return plain text (strip all HTML tags)

**Implementation:**
- Wrap existing `convertHtmlToMarkdown` in try-catch
- Add simple fallback that strips HTML tags
- Log which conversion method worked
